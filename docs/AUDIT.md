## Блокеры

### B1. Из контракта потерян `accessHash` — чаты не открываются и сообщения не отправляются

`domain.Chat` (`server/internal/core/domain/chat.go:9`) хранит только числовой `ID`. Клиент
получает его, шлёт обратно строкой, а адаптер собирает пир вручную:

```go
Peer: &tg.InputPeerUser{UserID: chatID}        // message.go:36, message.go:90
Peer: &tg.InputPeerChannel{ChannelID: chatID}  // message.go:43, message.go:99
```

`tg.InputPeerUser` и `tg.InputPeerChannel` требуют обязательное поле `AccessHash int64` — здесь
оно нулевое. Telegram отвечает `PEER_ID_INVALID` / `CHANNEL_INVALID` на всё, кроме чатов,
случайно оказавшихся в кэше сессии.

Дополнительно теряется **тип** чата: он известен на этапе `mapTelegramDialogs`
(`mapper.go:54-87`), но в запрос не передаётся, поэтому `message.go:41-49` и `message.go:97-102`
угадывают его перебором — сначала `InputPeerUser`, при ошибке `InputPeerChannel`. Обычная
группа (`InputPeerChat`) не покрыта вообще, а `err` первой попытки затирается и в лог не
попадает, из-за чего настоящая причина отказа не видна.

**Исправление:** `peerRef` по [API.md §2.1](./API.md). `accessHash` берётся из `userMap`/`chatMap`
там же, где сейчас берётся заголовок чата.

### B2. Превью последнего сообщения берётся из чужого чата

```go
func compileMessageMap(messages []tg.MessageClass) map[int]*tg.Message {  // mapper.go:28
    msgMap[msg.ID] = msg                                                  // mapper.go:32
```

`MessagesDialogs.Messages` — плоский список последних сообщений **всех** диалогов, а `msg.ID`
уникален только внутри одного чата. У каналов нумерация своя и начинается с 1, поэтому у
нескольких каналов одновременно есть сообщения с id `1`, `2`, `3`. Ключ-коллизия: в карте
остаётся последнее записанное, и `msgMap[d.TopMessage]` (`mapper.go:91`) возвращает сообщение
постороннего чата.

Видимый эффект: в списке чатов у части диалогов текст и время последнего сообщения — не свои.

**Исправление:** ключ `(peerID, msgID)`, а не `msgID`.

### B3. Переключение чата не перезагружает сообщения

`App.tsx:46-61`:

```jsx
<Show when={activeChatId() !== null}>
  <ChatWindow chatId={activeChatId()!} chatTitle={activeChatTitle()} ... />
</Show>
```

`ChatWindow` грузит историю в `onMount` (`chat-window/index.tsx:21-23`). Не-keyed `Show`
пересоздаёт потомка только когда условие меняет истинность. При переходе с чата A на чат B
условие остаётся `true`, потомок не размонтируется, `onMount` второй раз не срабатывает —
`openChat` не вызывается.

Заголовок при этом обновляется, потому что `props.chatTitle` реактивен. Итог: **начиная со
второго чата пользователь видит новый заголовок и сообщения предыдущего чата.**

**Исправление:** `createEffect(on(() => props.chatRef, load))` либо `<Show keyed>`, см.
[API.md §5.1](./API.md).

### B4. Состав папок вычисляется неверно

`chat.go:60-84` берёт только `f.IncludePeers` у значений, скастовавшихся к `*tg.DialogFilter`.
Игнорируется всё остальное, что определяет папку:

| Поле MTProto | Что теряется |
|---|---|
| `PinnedPeers` | закреплённые в папке чаты просто исчезают |
| `Contacts` / `NonContacts` / `Groups` / `Broadcasts` / `Bots` | папки вида «Личные», «Группы», «Каналы» имеют пустой `IncludePeers` и наполняются этими предикатами — сейчас такие папки **всегда пустые** |
| `ExcludePeers`, `ExcludeMuted`, `ExcludeRead`, `ExcludeArchived` | исключения не применяются, в папке лишние чаты |
| `*tg.DialogFilterChatlist` | папки-ссылки отбрасываются в `chat.go:62-64` и не показываются вовсе |

Плюс сопоставление идёт по числовому id (`chat-list/store.ts:38-43`), что после введения
`peerRef` всё равно надо переводить на `ref`.

**Исправление:** сервер вычисляет итоговый `chatRefs`, [API.md §3.4](./API.md).

### B5. Скачивание медиа не работает — пустой `fileReference`

```go
FileReference: []byte{}, // Для тестов пустой референс, в продакшене извлекается из сообщения
```
`media.go:53` и `media.go:59`.

`upload.getFile` с пустым `fileReference` возвращает `FILE_REFERENCE_EMPTY`. Комментарий в коде
признаёт заглушку. При этом `mediaID` формата `doc_<id>_<hash>` (`mapper.go:141,145`) в принципе
не позволяет восстановить reference — он привязан к конкретному сообщению.

**Исправление:** `mediaRef` вида `<peerRef>/<messageId>/<kind>`, [API.md §2.2](./API.md).

## Серьёзные

### S1. Время сообщений уезжает на таймзону сервера

`handler_messenger.go:116,120,139`:

```go
CreatedAt: m.CreatedAt.Format("2006-01-02T15:04:05Z")
```

В Go-раскладке специальными являются `Z0700` и `Z07:00`; одиночная `Z` — **литерал**. Значение
при этом остаётся локальным (`time.Unix` возвращает local). Проверено на машине в UTC+4:

```
момент времени : 2025-09-07 17:00:00 +0400
текущий формат : 2025-09-07T17:00:00Z   ← клиент читает это как UTC
правильно      : 2025-09-07T13:00:00Z
```

Сдвиг на 4 часа. В Docker-образе (`alpine`, UTC) совпадает случайно, при локальном `go run` —
нет; в проде поедет при любой ненулевой TZ хоста.

Отдельно: нулевое время сериализуется как `0001-01-01T00:00:00Z` (у `CreatedAt` нет `omitempty`),
и `formatDate` рисует такому чату «1 янв.».

**Исправление:** `m.CreatedAt.UTC().Format(time.RFC3339)`, отсутствующее время — `omitempty`.

### S2. Отправленное сообщение рисуется как чужое

`message.go:130-138` возвращает заглушку: `SenderID: 0`, `Out` не выставлен, `CreatedAt` —
локальное время клиента-сервера, а при неудачном разборе `updates` ещё и `ID` синтетический
(`message.go:107`, `randomID & 0x7FFFFFFF`). Клиент определяет своё сообщение сравнением
`senderId === ownUserId` (`chat-window/store.ts:101-103`), поэтому пузырь уходит влево, как
входящий.

### S3. `ownUserId` может быть нулём в момент открытия чата

`ownUserId` инициализируется нулём (`chat-list/store.ts:7`) и заполняется только после
`loadDashboard`, который запускается в `onMount` списка чатов. `ChatWindow` получает его
значением через `props` и копирует в обычную переменную `currentOwnUserId`
(`chat-window/store.ts:12,26`) — **не сигнал**, то есть последующее обновление до неё не дойдёт.

Вместе с S2 это значит, что выравнивание сообщений ненадёжно в принципе. По
[API.md §5.5](./API.md) признак — `message.out`, и обе проблемы исчезают.

### S4. Пагинация диалогов сломана

`chat.go:26-30` передаёт `OffsetID: offset` при `OffsetPeer: &tg.InputPeerEmpty{}` и без
`OffsetDate`. В `messages.getDialogs` `OffsetID` — это id **сообщения** (top_message), а не
порядковый номер, и курсор диалогов состоит из тройки `(OffsetDate, OffsetID, OffsetPeer)`.
Сейчас клиент всегда шлёт `offset: 0` (`client.ts` → `loadDashboard(100, 0)`), поэтому баг
латентный, но вторая страница чатов не заработает никогда.

### S5. Клиент пересортировывает чаты и теряет порядок Telegram

`chat-list/store.ts:45-49` сортирует по `lastMessage.createdAt`. Telegram уже отдаёт диалоги в
правильном порядке с закреплёнными наверху; `Dialog.Pinned` в `domain.Chat` вообще не
переносится (`mapper.go:89` берёт только `UnreadCount`). После сортировки пины перемешиваются с
остальными, а чаты, у которых `lastMessage` не нашёлся из-за B2, уезжают в конец списка с
нулевой датой.

### S6. `SESSION_EXPIRED` не обрабатывается — пользователь застревает в мёртвом интерфейсе

`initFromStorage` (`auth/store.ts:100-110`) ставит статус `AUTHORIZED` по одному факту наличия
строки в `localStorage`, без проверки. Токен живёт 24 часа в Redis, MTProto-клиент — только в
памяти процесса. После рестарта бэкенда или истечения TTL пользователь попадает в интерфейс,
получает ошибку на `dashboard` и остаётся с пустым экраном без возможности перелогиниться.
Перехватчик ответов (`client.ts`) переводит любую ошибку в `new Error(msg)` и статус теряет.

Нужен `GET /auth/session` при старте и разлогин по `SESSION_EXPIRED` в перехватчике.

### S7. Сервер отдаёт 47 полей на сообщение, клиент рисует два

`messageDTO` (`handler_messenger.go:33-68`) — 47 JSON-полей. `MessageItem.tsx` использует
`text` и `createdAt`. Не отрисовывается ничего из того, что уже передаётся: `entities`
(жирный, ссылки, спойлеры — всё рендерится плоским текстом), `hasMedia`/`mediaId` (медиа не
показывается вообще, хотя эндпоинт стриминга есть), `replyToMsgId` (нет превью ответа),
`fwdFromName`, `views`, `editDate`.

На дашборде это ×100 чатов в каждом ответе. Контракт надо сузить до отрисовываемого
([API.md §3.3](./API.md)) и параллельно завести задачи на сам рендер.

### S8. `ErrChatNotFound` отдаётся как 401

`handler_messenger.go:182-184` мапит `ErrChatNotFound` в `StatusUnauthorized`. При этом
`ErrChatNotFound` возвращается и при пустом `ChatID` (`messenger/dto.go:52-54`). Клиент не может
отличить «плохой запрос» от «сессия протухла» — и это ровно тот случай, где по S6 нужен
автоматический разлогин. Правильно: `PEER_INVALID` 400 / `PEER_NOT_FOUND` 404.

## Прочее

**Контракт**

1. Три конвенции именования в одном ответе: верхний уровень — `chats`, `folders`, `messages`;
   внутри объектов — `ID`, `Title`, `SenderID`; внутри entity — `offset`, `length`
   (`handler_messenger.go:17-80`). Клиент вынужден держать ручной слой переименования
   (`client.ts`, функции `mapChat`/`mapMessage`/`mapFolder`) — постоянный источник рассинхрона.
2. `OwnUserID` (`handler_messenger.go:79`) — единственный ключ верхнего уровня с заглавной буквы.
3. `Chat.Type` — числовой enum `0|1|2` с ручным маппингом на клиенте (`client.ts:mapChatType`).
   Вставка значения в середину молча ломает клиент.
4. `ChatID` передаётся строкой в запросах, но числом в ответах.
5. `MessageEntityPre.Language` кладётся в поле `URL` (`mapper.go:229`) — семантически чужое поле.
6. Ответ `logout` — `{}` вместо `204`.
7. Нет `GET /health` — оркестратору нечего опрашивать.
8. `FLOOD_WAIT` не обрабатывается нигде; ошибка уходит как 500 без `retryAfter`.
9. `ErrDashboardFailed` (`load_dashboard_usecase.go:52`) схлопывает любую из трёх параллельных
   ошибок в одну строку — причина отказа теряется до логов.

**Безопасность**

10. JWT генерируется, но `ValidateToken` (`lib/jwt/jwt.go:38`) не вызывается ни разу — подпись не
    проверяется, токен работает просто как ключ Redis. Любая строка, попавшая в Redis, валидна.
11. Клиент шлёт `Authorization: Bearer` (`client.ts`, перехватчик запросов), сервер его не читает —
    токен берётся из тела. Заголовок мёртвый.
12. Токен медиа передаётся в query (`client.ts:getMediaUrl`, `handler_media.go:24`) и оседает в
    access-логах nginx и в истории браузера. `access_log off` в `client/nginx.conf` стоит только
    на статике.
13. `writeError` (`response.go:21`) собирает JSON конкатенацией — кавычка или перевод строки в
    `err.Error()` ломает тело ответа. Туда же уходит `err.Error()` целиком
    (`handler_auth.go:75`, `handler_messenger.go:210`), то есть наружу утекают обёрнутые ошибки
    gotd с внутренними деталями.
14. CORS открыт на `*` (`middleware.go:11`) при том, что фронт и API за одним nginx — заголовок
    вообще не нужен.
15. `JWT_SECRET=super-secret-key` в `docker-compose.yaml:29`.

**Клиент**

16. Активный чат дублируется: `App.tsx:11-12` и `chat-window/store.ts:6-8`. Два источника правды.
17. Ключ списка чатов — `chat.id` (`chat-list/index.tsx:51-58`), после `peerRef` перейдёт на `ref`.
18. Слой IndexedDB (`core/db/schema.ts`, 110 строк) написан полностью и не вызывается ниоткуда.
19. Алиас `~` настроен в `vite.config.ts`, но нигде не используется — везде относительные пути
    вида `../../../types`.
20. Аватары не грузятся: `Avatar` рисует инициалы, эндпоинта для фото профиля нет.
21. Нет отметки прочитанного (`messages.readHistory`) и разделителя непрочитанных — `unreadCount`
    показывается, но никогда не сбрасывается.

**Сервер**

22. `middlewareLogger` (`middleware.go:37`) объявлен и не подключён в цепочку
    (`server.go:57`); к тому же он логирует статус до вызова `next`, то есть всегда `200`.
23. Обработка `OPTIONS` продублирована в `router.go:22-25` и `middleware.go:16-19`; первая
    недостижима.
24. `Server.Addr()` (`server.go:97`) и порт `:8080` (`server.go:67`) захардкожены, конфига нет.
25. Пул MTProto-клиентов живёт в памяти процесса (`adapter.go:37`), горизонтального
    масштабирования нет — нужны sticky-сессии или вынесение пула.
26. В git закоммичены `server/app` (23 МБ бинарник, постоянно «модифицирован»),
    `server/repomix.txt`, пустой `server/1`; корневого `.gitignore` нет.

## Порядок работ

Разбито так, чтобы каждый шаг был отдельным проверяемым коммитом.

**Шаг 1 — фундамент контракта (закрывает B1, B4 частично, S8, п.1-5)**
`peerRef` в домене и DTO; `lowerCamelCase` везде; строковые enum'ы; структурированные ошибки;
RFC3339 UTC (S1). Затрагивает `domain/`, `handler_*.go`, `client.ts`, `types/index.ts`.
После шага маппинг на клиенте схлопывается до парсинга дат.

**Шаг 2 — корректность данных о чатах (B2, B4, S4, S5)**
Ключ `(peer, msgId)` в `compileMessageMap`; полный расчёт состава папок; курсорная пагинация;
перенос `pinned`/`order` в `domain.Chat`; снятие сортировки на клиенте.

**Шаг 3 — отрисовка (B3, S2, S3, S6)**
Перезагрузка по смене `peerRef`; `out` как признак своего сообщения; полноценный `Message` в
ответе на отправку; `GET /auth/session` и разлогин по `SESSION_EXPIRED`.

**Шаг 4 — медиа (B5)**
`mediaRef` с перезапросом `fileReference`, `Range`-стриминг, отрисовка вложений, аватары.

**Шаг 5 — гигиена**
Валидация JWT, токен только в заголовке, `writeError` через сериализатор, `/health`,
`FLOOD_WAIT`, подключение логгера, `.gitignore` и вычистка бинарника из индекса.

Все пять шагов выполнены.

## Что осталось незакрытым

Осознанно отложено, в контракте помечено как «планируется»:

- **Аватары чатов** — эндпоинта нет, `Avatar` по-прежнему рисует инициалы.
- **Отметка прочитанного** (`messages.readHistory`) — `unreadCount` показывается, но не сбрасывается.
- **Live-обновления** — новые сообщения не приходят без перезагрузки; MTProto updates не подписаны.
- **Пагинация в UI** — сервер отдаёт `nextCursor` и `nextBeforeId`, клиент их пока не использует:
  грузится первая страница на 100 чатов и 50 сообщений.
- **Горизонтальное масштабирование** — пул MTProto-клиентов остался в памяти процесса, для
  нескольких реплик нужны sticky-сессии или вынесение пула.
- **История git** — бинарник `server/app` убран из индекса и в `.gitignore`, но его 23 МБ
  остались в прошлых коммитах. Чистка требует перезаписи истории и отдельного решения.
