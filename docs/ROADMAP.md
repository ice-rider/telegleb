# Roadmap

План развития Telegleb до полноценного клиента. Порядок не случайный: каждый
этап опирается на контракт и инфраструктуру предыдущего. Пункты внутри этапа
можно тасовать, этапы между собой — нет.

Правило то же, что и в [API.md](./API.md): формат данных меняется сначала в
спеке, потом в обеих реализациях.

**Условные обозначения:** ✅ сделано · 🔨 в работе · ⬜ не начато

## Этап 1 — живой мессенджер

Сейчас клиент статичен: новые сообщения не приходят, прочитанное не
сбрасывается. Без этого этапа всё остальное — просмотрщик, а не мессенджер.

| | Что | Чем делается |
|---|---|---|
| ⬜ | **Live-обновления** | `updates.getDifference` + `channels.getChannelDifference`, состояние pts/qts/date в Redis; наружу WebSocket или SSE |
| ⬜ | Новые сообщения без перезагрузки | `updateNewMessage`, `updateNewChannelMessage`, `updateEditMessage`, `updateDeleteMessages` |
| ⬜ | Отметка прочитанного | `messages.readHistory`, `channels.readHistory`, для тем — `messages.readDiscussion` |
| ⬜ | Индикатор «печатает» | `updateUserTyping`, `messages.setTyping` |
| ⬜ | Статус «в сети» / «был(а)» | `updateUserStatus`, `UserStatus*` |
| ⬜ | Пагинация истории в UI | сервер уже отдаёт `nextBeforeId`, клиент подгружает при скролле вверх |
| ⬜ | Пагинация диалогов в UI | сейчас грузится всё до потолка; нужна ленивая догрузка |

**Ключевое решение этапа:** канал доставки. WebSocket даёт двусторонность
(typing, read-квитанции), SSE проще и переживает прокси без настройки. При
одном инстансе разницы почти нет; при нескольких — оба упираются в то, что
пул MTProto-клиентов живёт в памяти процесса (см. этап 7).

## Этап 1.5 — приоритетная загрузка (киллер-фича)

**Задача.** Пользователь помечает чаты как приоритетные. При входе и при
догоне обновлений они грузятся первыми, а не в общей куче. Больной сценарий:
после долгого отсутствия клиент вразнобой тянет всё подряд, и пока
прогружаются архивные чаты с тысячами сообщений, личка ждёт.

Такого понятия в Telegram нет — это наша собственная надстройка.

### Почему это вообще возможно

В MTProto **нет** метода «дай чаты папки N»: `folder_id` в `messages.getDialogs`
означает архив (0 или 1), а не пользовательские папки. Зато есть
`messages.getPeerDialogs(peers)` — выборка ровно перечисленных пиров одним
запросом. Приоритетный список это ровно такой набор пиров, поэтому его можно
получить одним обращением, не дожидаясь полного списка диалогов.

Тот же приём уже используется для явных участников папок (этап 0).

### Хранение

Приоритет — состояние приложения, а не Telegram, значит живёт у нас:

```
Redis: telegleb:priority:<userID> → SET из peerRef
```

Ключ по `userID`, а не по токену сессии: пометки должны переживать
перелогин и совпадать между устройствами.

| | Что |
|---|---|
| ⬜ | `PUT /chats/{ref}/priority` и `DELETE /chats/{ref}/priority` |
| ⬜ | `chat.priority: boolean` в контракте |
| ⬜ | Пометка в UI: контекстное меню чата, значок в карточке |
| ⬜ | Вкладка «Важное» рядом с «Все» и «Архив» |

### Загрузка в два фазы

```
фаза 1  getDialogFilters + getPeerDialogs(приоритетные)   → отдать сразу
фаза 2  полный список диалогов постранично                 → дослать
```

Ключевой момент: **раскладка по папкам считается для каждого чата
независимо**. Предикаты папки (`contacts`, `groups`, `broadcasts`, `bots`)
проверяются по атрибутам самого чата, а явные включения — по спискам из
описания папки. И то и другое известно уже в фазе 1, поэтому приоритетные
чаты приезжают сразу с правильными `folderIds` и `archived`.

Это не нарушает инвариант из [API.md §3.4](./API.md), но требует аккуратности
в формулировке. Запрещено показывать чат в **неправильной** папке и потом
убирать — именно этим раздражает официальный клиент. Разрешено показывать
**неполную** папку, которая затем дополняется, при условии что состояние
загрузки видно пользователю. Разница принципиальная: в первом случае
интерфейс врёт, во втором — честно говорит «ещё гружу».

| | Что |
|---|---|
| ⬜ | Разделить `GET /chats` на две фазы или добавить `?priorityOnly=1` |
| ⬜ | Доставка второй фазы: тем же каналом, что и live-обновления (этап 1) |
| ⬜ | Индикатор «загружено N из M» в списке чатов |

### Приоритет при догоне обновлений

`updates.getDifference` отдаёт накопленное одной пачкой, переупорядочить её
нельзя. Приоритет применяется к тому, что происходит **после** разбора пачки:

| | Что |
|---|---|
| ⬜ | Сначала применять и отрисовывать апдейты приоритетных чатов |
| ⬜ | Предзагрузка истории только для приоритетных; остальные — по открытию |
| ⬜ | Архивные чаты не префетчить никогда, если не помечены приоритетными |
| ⬜ | При `updates.differenceTooLong` — повторная загрузка тоже в две фазы |

### Зависимости

Требует этапа 1 (live-обновления): без канала доставки вторую фазу некуда
дослать, а приоритет при догоне обновлений нечему применять. Пометку чатов и
вкладку «Важное» можно сделать раньше — они самодостаточны.

## Что делать следующим

Рекомендуемый порядок на ближайшее время:

1. **Аватары** (этап 2) — маленькая задача, самый заметный эффект.
2. **Отметка прочитанного** (этап 1) — счётчики непрочитанного сейчас врут,
   потому что никогда не сбрасываются.
3. **Пометка чатов приоритетными** (этап 1.5) — самодостаточная часть
   киллер-фичи: хранение, эндпоинты, вкладка «Важное». Делается независимо
   от live-обновлений и сразу даёт пользу.
4. **Live-обновления** (этап 1) — самая крупная задача, после неё приложение
   перестаёт быть просмотрщиком.
5. **Приоритетная загрузка целиком** (этап 1.5) — после live.

Ответы, реакции и редактирование (этап 3) дешевле делать уже после live —
иначе результат каждого действия придётся дорисовывать вручную.
