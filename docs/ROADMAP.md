# Roadmap

План развития Telegleb до полноценного клиента. Порядок не случайный: каждый
этап опирается на контракт и инфраструктуру предыдущего. Пункты внутри этапа
можно тасовать, этапы между собой — нет.

Правило то же, что и в [API.md](./API.md): формат данных меняется сначала в
спеке, потом в обеих реализациях.

**Условные обозначения:** ✅ сделано · 🔨 в работе · ⬜ не начато

## Этап 1 — живой мессенджер

Сейчас клиент статичен: новые сообщения не приходят, прочитанное не
сбрасывается. Без этого этапа всё остальное — просмотрщик, а не мессенджер.

| | Что | Чем делается |
|---|---|---|
| ⬜ | **Live-обновления** | `updates.getDifference` + `channels.getChannelDifference`, состояние pts/qts/date в Redis; наружу WebSocket или SSE |
| ⬜ | Новые сообщения без перезагрузки | `updateNewMessage`, `updateNewChannelMessage`, `updateEditMessage`, `updateDeleteMessages` |
| ⬜ | Отметка прочитанного | `messages.readHistory`, `channels.readHistory`, для тем — `messages.readDiscussion` |
| ⬜ | Индикатор «печатает» | `updateUserTyping`, `messages.setTyping` |
| ⬜ | Статус «в сети» / «был(а)» | `updateUserStatus`, `UserStatus*` |
| ⬜ | Пагинация истории в UI | сервер уже отдаёт `nextBeforeId`, клиент подгружает при скролле вверх |
| ⬜ | Пагинация диалогов в UI | сейчас грузится всё до потолка; нужна ленивая догрузка |

**Ключевое решение этапа:** канал доставки. WebSocket даёт двусторонность
(typing, read-квитанции), SSE проще и переживает прокси без настройки. При
одном инстансе разницы почти нет; при нескольких — оба упираются в то, что
пул MTProto-клиентов живёт в памяти процесса (см. этап 7).

## Этап 2 — аватары и медиа

| | Что | Чем делается |
|---|---|---|
| ⬜ | **Аватары чатов и пользователей** | `InputPeerPhotoFileLocation`, эндпоинт `GET /avatars/{ref}?size=small\|big`, кэш на диске + `Cache-Control` |
| ⬜ | Просмотр видео с перемоткой | `Range` уже поддержан сервером; нужен плеер и превью-постер |
| ⬜ | Голосовые и кружки | `DocumentAttributeAudio.waveform`, отрисовка волны |
| ⬜ | Стикеры и анимированные эмодзи | статические сразу, `.tgs` (lottie) — отдельная задача |
| ⬜ | Альбомы | группировка по `groupedId`, он уже есть в MTProto-ответе |
| ⬜ | **Отправка файлов** | `messages.uploadMedia`, `upload.saveFilePart`, прогресс загрузки |
| ⬜ | Превью ссылок | `MessageMediaWebPage` |

Аватары стоит делать первыми: список чатов с инициалами вместо фото — самое
заметное визуальное отличие от настоящего клиента.

## Этап 7 — эксплуатация

Технический долг, который начнёт мешать по мере роста.

| | Что | Почему |
|---|---|---|
| ⬜ | **Вынести пул MTProto-клиентов из памяти процесса** | сейчас бэкенд нельзя масштабировать и нельзя перезапустить без разрыва сессий |
| ⬜ | Graceful-переподключение к Telegram | при обрыве клиент пересоздаётся только на следующем запросе |
| ⬜ | Кэш дашборда | загрузка всех диалогов — это до 15 запросов к Telegram на каждый вход |
| ⬜ | Локальный кэш на клиенте | с оговоркой из [API.md §5](./API.md): кэшированный чат нельзя рисовать раньше, чем известна его папка |
| ⬜ | Метрики и трассировка | сейчас только логи |
| ⬜ | Автопродление TLS (certbot) | сертификат ручной, истекает 22.11.2026 |
| ⬜ | CI: тесты и сборка на PR | workflow сейчас только собирает образы |
| ⬜ | Мобильная вёрстка | интерфейс рассчитан на десктоп |

## Что делать следующим

Рекомендуемый порядок на ближайшее время:

1. **Аватары** (этап 2) — маленькая задача, самый заметный эффект.
2. **Отметка прочитанного** (этап 1) — счётчики непрочитанного сейчас врут,
   потому что никогда не сбрасываются.
3. **Live-обновления** (этап 1) — самая крупная задача этапа, после неё
   приложение перестаёт быть просмотрщиком.

Ответы, реакции и редактирование (этап 3) дешевле делать уже после live —
иначе результат каждого действия придётся дорисовывать вручную.
