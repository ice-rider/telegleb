# Telegleb API — спецификация контракта v1

**Статус:** нормативная и реализованная. Это единственный источник правды по формату обмена
между `client/` и `server/`. Код, расходящийся с этим документом, — баг.

**Правило:** любое изменение формата данных вносится сначала сюда, потом в обе реализации.
Менять DTO только на одной стороне запрещено — именно так появились расхождения, разобранные
в [AUDIT.md](./AUDIT.md).

---

## 1. Общие соглашения

### 1.1 Транспорт

- Базовый префикс: `/api/v1`.
- Тело запроса и ответа — `application/json; charset=utf-8`.
- Чтение — `GET` (параметры в query), действия — `POST` (параметры в теле).
- Единственный ответ без JSON — стриминг медиа (`application/octet-stream` или тип файла).

### 1.2 Именование

**Все ключи JSON — `lowerCamelCase`, на всех уровнях вложенности, в запросах и в ответах.**

Никаких `PascalCase`, никаких `ID`/`URL` капсом: `id`, `chatId`, `url`, `folderIds`.
Аббревиатура в конце имени пишется как обычное слово: `senderId`, а не `senderID`.

В Go это означает обязательный явный тег на каждом поле DTO:

```go
type messageDTO struct {
    ID       int64 `json:"id"`
    ChatRef  string `json:"chatRef"`
    SenderID int64 `json:"senderId"`
}
```

Имена полей на клиенте совпадают с JSON один в один, поэтому слоя переименования между сетью
и приложением нет — и рассинхронизироваться нечему.

### 1.3 Числа и идентификаторы

| Что | Тип в JSON | Почему |
|---|---|---|
| `id` пользователя, чата, сообщения | `number` | Telegram держит их существенно ниже 2^53 |
| `accessHash`, `fileReference` | **не передаются отдельно** | входят в непрозрачные `ref`, см. §2 |
| `ref` чата, `ref` медиа | `string` | содержат int64 полного диапазона |
| счётчики (`unreadCount`, `views`) | `number` | |

Клиент **никогда** не собирает `ref` сам и не разбирает его. Он получает строку от сервера и
возвращает её обратно как есть.

### 1.4 Время

- Формат — **RFC 3339 в UTC**: `2026-09-07T13:00:00Z`.
- В Go — только `t.UTC().Format(time.RFC3339)`. Раскладка `"2006-01-02T15:04:05Z"` **запрещена**:
  буква `Z` в ней литерал, время при этом остаётся локальным, и клиент получает сдвиг на
  таймзону сервера. Проверяется тестом `TestFormatTimeIsAlwaysUTC`.
- Отсутствующего времени не существует: поле либо есть с валидным значением, либо **отсутствует
  в JSON** (`omitempty`). Нулевая дата `0001-01-01T00:00:00Z` не передаётся никогда.

### 1.5 Аутентификация

- Токен сессии передаётся **только** заголовком: `Authorization: Bearer <sessionToken>`.
- В теле запроса и в query-строке его нет: в query он оседает в access-логах nginx и в истории
  браузера.
- Токен выдаёт `POST /auth/request-code`. Клиент хранит его в `localStorage` под ключом
  `telegleb.sessionToken`.
- Медиа требует того же заголовка, поэтому клиент грузит вложения через `fetch` +
  `URL.createObjectURL`, а не через `<img src>`.

### 1.6 Ошибки

Любой ответ с кодом ≥ 400 имеет ровно такое тело:

```json
{ "error": { "code": "SESSION_EXPIRED", "message": "session expired" } }
```

- `code` — машиночитаемый, из закрытого списка. **Клиент ветвится только по `code`.**
- `message` — фиксированный текст для лога. Он не является контрактом и не показывается
  пользователю: клиент подбирает формулировку сам по `code`.
- Внутренние ошибки (обёрнутые ошибки gotd, адреса DC) в `message` не попадают никогда.
- Тело формируется сериализатором, а не конкатенацией строк.

| `code` | HTTP | Когда |
|---|---|---|
| `INVALID_BODY` | 400 | тело не парсится или не проходит валидацию |
| `INVALID_PHONE` | 400 | номер не в формате `+<цифры>` |
| `INVALID_CODE` | 401 | неверный код подтверждения |
| `INVALID_PASSWORD` | 401 | неверный пароль 2FA |
| `SESSION_EXPIRED` | 401 | токена нет, он протух или подпись невалидна |
| `SESSION_INVALID_STATE` | 409 | шаг авторизации вызван не по порядку |
| `PEER_INVALID` | 400 | `ref` чата не разбирается |
| `PEER_NOT_FOUND` | 404 | Telegram не знает такой peer / нет доступа |
| `MESSAGE_EMPTY` | 400 | пустой текст сообщения |
| `MEDIA_NOT_FOUND` | 404 | `ref` медиа не разбирается или файл недоступен |
| `FLOOD_WAIT` | 429 | Telegram вернул `FLOOD_WAIT_x`; тело содержит `retryAfter` (секунды) |
| `TELEGRAM_ERROR` | 502 | прочая ошибка MTProto |
| `INTERNAL` | 500 | всё остальное |
| `NOT_FOUND` / `METHOD_NOT_ALLOWED` | 404 / 405 | маршрутизация |

```json
{ "error": { "code": "FLOOD_WAIT", "message": "too many requests, retry later", "retryAfter": 42 } }
```

**Реакция клиента на `SESSION_EXPIRED` единая и обязательная:** очистить `localStorage`,
сбросить состояние авторизации, показать экран входа. Это делается в перехватчике axios,
а не в каждом вызове.

### 1.7 Пагинация

Курсорная, не оффсетная. Смещение числом в MTProto не работает: курсор диалогов — это тройка
`(offset_date, offset_id, offset_peer)`, курсор истории — id сообщения.

- Запрос принимает `limit` (по умолчанию 30, максимум 100) и необязательный `cursor`.
- Ответ возвращает `nextCursor` (для диалогов) или `nextBeforeId` (для истории);
  отсутствие поля означает, что данные кончились.
- Курсор для клиента непрозрачен.

## 2. Идентификаторы

### 2.1 `ref` чата

MTProto для обращения к пользователю или каналу требует пару `(id, accessHash)`. Передавать
только числовой `id` бессмысленно: любой запрос к каналу получает `PEER_ID_INVALID`, а
угадывание типа перебором это не лечит, лишь маскирует ошибку.

`ref` — строка, несущая вид, id и хеш доступа:

```
user:<userId>:<accessHash>
chat:<chatId>                    # обычная группа, accessHash не нужен
channel:<channelId>:<accessHash> # канал и супергруппа
```

Пример: `channel:1234567890:-8901234567890123456`.

- Формирует и разбирает **только сервер** (`domain.Peer`, тесты `peer_test.go`).
- Клиент использует `ref` как идентификатор чата, ключ списка и параметр всех запросов.
- Числовое `chat.id` остаётся для отображения и отладки, но **адресом не является**.

### 2.2 `ref` медиа

`fileReference` у Telegram протухает, поэтому хранить его в идентификаторе бесполезно.
`ref` вместо этого указывает, **откуда файл можно перезапросить**:

```
<refЧата>~<messageId>~<kind>
```

Пример: `channel:123:-456~78901~photo`.

Разделитель `~`, а не `/`, чтобы `ref` оставался одним сегментом URL. Сервер по нему заново
получает сообщение (`messages.getMessages` / `channels.getMessages`), достаёт свежий
`fileReference` и только потом качает чанк.

## 3. Схемы данных

### 3.1 `Me`

```json
{ "id": 123456789, "firstName": "Глеб", "lastName": "", "username": "gleb", "phone": "+79000000000" }
```

### 3.2 `Chat`

```json
{
  "ref": "channel:1234567890:-8901234567890123456",
  "id": 1234567890,
  "type": "channel",
  "title": "Название",
  "unreadCount": 3,
  "unreadMentionsCount": 0,
  "markedUnread": false,
  "pinned": true,
  "muted": false,
  "archived": false,
  "folderIds": [2, 5],
  "order": 0,
  "lastMessage": { "...": "Message, отсутствует если чат пуст" }
}
```

- `type` — **строка**: `"direct" | "group" | "channel"`. Числовой enum запрещён: вставка
  значения в середину молча ломает клиент. Супергруппа отдаётся как `"group"`.
- **`archived` и `folderIds` — резолв сервера, и они лежат на самом чате.** Это ключевое
  решение контракта, см. §3.4.
- `order` — позиция в порядке, который вернул Telegram, отдельно для основного списка и для
  архива, начиная с 0. **Клиент выводит чаты по `order` и не пересортировывает их.** Telegram
  уже учёл закреплённые чаты и время; локальная сортировка по дате ломает и то, и другое.
- `lastMessage` — полноценный `Message`. Если сообщения нет, поле отсутствует.

### 3.3 `Message`

Контракт сообщения намеренно узкий: поле добавляется, **только когда его кто-то рисует**.
Раздутый DTO — это трафик на каждом из сотни чатов дашборда и лишняя поверхность для
рассинхрона.

```json
{
  "id": 78901,
  "chatRef": "channel:1234567890:-8901234567890123456",
  "senderId": 123456789,
  "senderName": "Глеб",
  "out": true,
  "text": "привет",
  "createdAt": "2026-09-07T13:00:00Z",
  "editedAt": "2026-09-07T13:05:00Z",
  "entities": [{ "offset": 0, "length": 6, "type": "bold" }],
  "media": { "ref": "channel:123:-456~78901~photo", "kind": "photo", "mimeType": "image/jpeg", "size": 51234, "width": 1280, "height": 720 },
  "replyTo": { "id": 78900, "senderName": "Аня", "text": "как дела?" },
  "forwardedFrom": "Название канала",
  "views": 0,
  "pinned": false
}
```

- **`out` — единственный признак «моё сообщение».** Клиент выравнивает пузырь по нему, а не
  сравнивает `senderId` с id профиля: у каналов отправитель — сам канал, а профиль на момент
  первой отрисовки может быть ещё не загружен.
- `senderName` резолвится на сервере из словарей `users`/`chats` ответа MTProto.
- `editedAt`, `media`, `replyTo`, `forwardedFrom`, `views`, `pinned` опциональны и при
  отсутствии **опускаются**.
- `entities.type` — из закрытого списка: `bold`, `italic`, `underline`, `strike`, `spoiler`,
  `code`, `pre`, `blockquote`, `url`, `text_url`, `mention`, `mention_name`, `hashtag`,
  `bot_command`, `email`, `phone`. Неизвестные серверу типы **не передаются**.
  У `text_url` заполняется `url`, у `mention_name` — `userId`, у `pre` — `language`.
  Смещения считаются в кодовых единицах UTF-16, что совпадает с индексацией строк в JS.
- `media.kind` — `photo | video | audio | voice | document | sticker | gif`.

### 3.4 `Folder` и главный инвариант раскладки

```json
{ "id": 2, "title": "Работа", "emoticon": "💼", "order": 0 }
```

**Папка описывает только вкладку. Её состава здесь нет — принадлежность живёт в
`chat.folderIds` и `chat.archived`.**

Это сделано ради одного свойства: **клиент не может отрисовать чат, не зная его размещения.**
Схема «список чатов отдельно, список папок отдельно» допускает кадр, в котором чаты уже
пришли, а раскладка ещё нет; официальный клиент Telegram именно так на долю секунды показывает
в общем списке архивные и чужие для вкладки чаты, которые затем исчезают. Когда размещение
приезжает тем же объектом, что и чат, такого кадра не существует в принципе.

Из этого следуют три обязательных правила:

1. Чаты, папки и профиль возвращаются **одним ответом** `GET /chats`. Отдельного эндпоинта
   для папок нет намеренно.
2. Фильтрация на клиенте читает поля самого чата (`chat.archived`, `chat.folderIds`) и
   **никогда** не соединяет список чатов со списком папок.
3. Пока ответ не получен целиком, не отрисовывается ни один чат. Если хоть одна часть
   (диалоги, архив, фильтры, профиль) не загрузилась — весь ответ считается неуспешным.
   Показать половину раскладки хуже, чем показать индикатор загрузки.

Сервер при вычислении `folderIds` учитывает всё, чем Telegram задаёт папку:

| Источник | Что даёт |
|---|---|
| `pinnedPeers` + `includePeers` | явно добавленные чаты |
| предикаты `contacts`, `nonContacts`, `groups`, `broadcasts`, `bots` | наполняют папки, у которых `includePeers` пуст — «Личные», «Каналы», «Группы», «Боты» |
| `excludePeers` | безусловное исключение |
| `excludeMuted`, `excludeRead`, `excludeArchived` | исключения для чатов, попавших по предикату |
| `dialogFilterChatlist` | папки-ссылки, наравне с обычными |
| `dialogFilterDefault` | «Все чаты» — вкладкой не приходит, ей соответствует `!archived` |

Явное включение сильнее флагов `exclude*`, но слабее `excludePeers`. Пиры сопоставляются по
виду и id **без учёта `accessHash`**: в описании папки он может отличаться или быть нулевым.
Всё покрыто тестами в `server/internal/adapter/telegram/folders_test.go`.

### 3.5 Архив

Архив — обычные чаты с `archived: true`. Он приезжает клиенту целиком вместе с первой
страницей и показывается отдельной вкладкой. В выдачу вкладки «Все» архивные чаты не попадают
никогда, потому что фильтр читает `chat.archived` на самом чате.

## 4. Эндпоинты

### 4.1 Авторизация

Заголовок `Authorization` требуется всем шагам, кроме `request-code`.

#### `POST /api/v1/auth/request-code`

```jsonc
// → { "phone": "+79000000000" }
// ← 200
{ "sessionToken": "eyJ...", "nextStep": "code", "codeType": "app", "timeout": 60 }
```

`codeType`: `app | sms | call | flashCall | missedCall | fragmentSms | email | unknown` —
клиент по нему пишет, куда смотреть за кодом.
Ошибки: `INVALID_PHONE`, `FLOOD_WAIT`, `TELEGRAM_ERROR`.

#### `POST /api/v1/auth/verify-code`

```jsonc
// → { "code": "12345" }
// ← 200
{ "nextStep": "password" }
{ "nextStep": "done", "me": { "...": "Me" } }
```

Ошибки: `INVALID_CODE`, `SESSION_EXPIRED`, `SESSION_INVALID_STATE`, `FLOOD_WAIT`.

#### `POST /api/v1/auth/verify-password`

```jsonc
// → { "password": "..." }
// ← 200
{ "nextStep": "done", "me": { "...": "Me" } }
```

#### `GET /api/v1/auth/session`

Проверка живости токена при старте приложения.

```jsonc
// ← 200
{ "status": "authorized", "me": { "...": "Me" } }
// ← 401 SESSION_EXPIRED
```

#### `POST /api/v1/auth/logout`

Тело пустое, ответ `204 No Content`. Сервер закрывает MTProto-клиент и удаляет сессию.

### 4.2 Чаты

#### `GET /api/v1/chats?limit=100&cursor=<opaque>`

Единственный эндпоинт дашборда: чаты, папки и профиль в одном ответе (см. §3.4).

```jsonc
// ← 200
{
  "chats": [ { "...": "Chat" } ],
  "folders": [ { "...": "Folder" } ],
  "me": { "...": "Me" },
  "nextCursor": "eyJkIjoxNzU3..."
}
```

Архив и список папок приезжают только с первой страницей (`cursor` пуст); `nextCursor`
относится к основному списку.

#### `GET /api/v1/chats/{ref}/messages?limit=50&beforeId=78901`

`beforeId` — id сообщения, старше которого нужна выдача; отсутствует при первой загрузке.

```jsonc
// ← 200
{ "messages": [ { "...": "Message" } ], "nextBeforeId": 78850 }
```

Сообщения отсортированы **по возрастанию** `id` — так их и рисует клиент.
Ошибки: `PEER_INVALID`, `PEER_NOT_FOUND`, `SESSION_EXPIRED`.

#### `POST /api/v1/chats/{ref}/messages`

```jsonc
// → { "text": "привет", "randomId": "l2k3j-8f14e45f" }
// ← 200
{ "message": { "...": "Message" } }
```

- `randomId` генерирует клиент; сервер использует его как ключ идемпотентности, поэтому
  повтор запроса с тем же значением не создаёт дубль.
- **Ответ содержит полностью заполненный `Message`** — с настоящим `id`, серверным `createdAt`
  и `out: true`. Заглушки недопустимы: из-за них отправленное сообщение рисуется как чужое.
- Тип пира берётся из `ref`; отправка перебором запрещена.

Ошибки: `MESSAGE_EMPTY`, `PEER_INVALID`, `PEER_NOT_FOUND`, `FLOOD_WAIT`.

### 4.3 Медиа

#### `GET /api/v1/media/{ref}`

Заголовки: `Authorization`, опционально `Range: bytes=<start>-`.

Без `Range` сервер собирает файл целиком (потолок 16 МБ) и отвечает `200`. С `Range` отдаёт
`206 Partial Content` с `Content-Range`. Смещение выравнивается вниз по границе 4096 байт —
этого требует `upload.getFile`, — и лишний префикс срезается из чанка.

Ошибки: `MEDIA_NOT_FOUND`, `SESSION_EXPIRED`.

### 4.4 Служебное

#### `GET /api/v1/health`

Без авторизации. `200 {"status":"ok","redis":"ok"}` либо `503`, если Redis недоступен.

### 4.5 Планируется

Не реализовано и в контракте пока отсутствует: аватары чатов (`GET /avatars/{ref}`), отметка
прочитанного (`messages.readHistory`), live-обновления через MTProto updates.

## 5. Правила отрисовки на клиенте

Часть контракта: без них корректные данные всё равно рисуются неверно.

1. **Ни один чат не рисуется, пока не получен весь ответ `GET /chats`.** Состояние дашборда —
   одно значение (`idle | loading | ready | error`), а не отдельные сигналы под чаты и папки:
   так наблюдатель не может увидеть чаты без раскладки.
2. **Фильтрация читает поля чата.** «Все» — `!chat.archived`, папка — `chat.folderIds.includes(id)`,
   «Архив» — `chat.archived`. Соединение с отдельным списком папок запрещено.
3. **Порядок чатов — серверный `order`.** Локальной сортировки нет.
4. **Ключ списка — `chat.ref`**, не индекс и не числовой `id`.
5. **Переключение чата обязано перезагружать сообщения.** Не-keyed `<Show>` не размонтирует
   потомка при смене чата, поэтому `onMount` второй раз не срабатывает. Загрузка привязана к
   действию «открыть чат», а `<Show keyed>` дополнительно пересоздаёт компонент.
6. **Своё сообщение определяется по `message.out`.**
7. **Единая обработка `SESSION_EXPIRED`** — в перехватчике axios, с полным разлогином.
   При старте приложения токен проверяется через `GET /auth/session`.
8. Активный чат хранится ровно в одном месте.
9. Текст ошибки выбирается по `error.code`, а не берётся из `error.message`.
10. Если появится локальный кэш (IndexedDB и т.п.), правило 1 распространяется и на него:
    показывать кэшированные чаты до того, как известна их раскладка, нельзя.
